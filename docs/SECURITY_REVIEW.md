# Security review and release limits

This review improves the implementation and tests its boundaries locally. **It is not a claim that a live deployment is secure.** The owner has not configured Supabase or Vercel. All live authorization, MFA, cloud storage, deployment, and recovery checks remain pending.

## Changes

- The October 2026 interface redesign (top/tab-bar navigation, dark mode, Cash flow, Accounts, Recurring, toasts, and dialogs) changes presentation only. Owner/MFA checks, encryption, memory-only keys, inactivity locking, backup verification, and the import review gates are unchanged. New views are derived from the unlocked in-memory state, and nothing is written to browser storage. The only new dependencies are the OFL-licensed `@fontsource-variable/inter` and `@fontsource-variable/source-serif-4` font files, bundled into the app's own static assets so the `font-src 'self'` policy still holds. Bank and merchant logos are inline SVG paths copied from Simple Icons (CC0) into `src/lib/brand-icons.ts` and from thesvg.org (MIT) for Capital One; merchant recognition is local pattern matching. No logos or fonts are fetched from other sites. The cash flow diagram is plain inline SVG built from the unlocked in-memory state (no new dependency). Dark mode adds one optional encrypted field, `preferences.theme` (`system`/`light`/`dark`); older vaults without it still validate and default to the device setting. The choice is applied as a `data-theme` attribute on the page, removed on lock/unmount, and never written to cookies or browser storage. Focus rings follow the last input type through a `data-input` attribute on the page; nothing is stored. The PDF parser changes for real Amex, Capital One, and Bank of America layouts are text-pattern rules only: no rendering, scripting, OCR, or network access was added, and the real statements used to check them stay outside the repository. Uploading several statements at once reuses the same worker per file, one at a time with the same limits, and still requires every saved statement to reconcile with its printed totals (automatically, or after per-statement review). Each one is saved as its own encrypted import batch with its own undo. The PDF worker now bundles the PDF.js **legacy** build of the same `pdfjs-dist` version, so slightly older browsers can parse statements. The worker's network-blocking CSP, script rejection, limits, and termination are unchanged and remain covered by browser tests.
- Both migrations enforce the one configured owner and JWT assurance `aal2`. RLS governs reads, inserts, and updates; direct write grants are revoked. The save RPC checks ownership/MFA and version, while a guard trigger checks ownership/MFA, encrypted-envelope shape, and version progression below the RPC. Every browser load/save independently checks the authenticated user, MFA assurance, and database owner access. The application has no service-role key or financial server endpoint.
- Tightened nested ciphertext validation, JSON value types, nonce/key-wrap lengths, payload limits, and returned version validation. AES-256-GCM uses 128-bit tags, independent random nonces, and context-specific authenticated data. Financial records and settings, including reconciliation evidence, are encrypted together before sending to Supabase.
- Key objects are non-extractable and retained only in memory. Temporary raw key/decrypted byte buffers are cleared where possible. Lock, sign-out, and unmount invalidate asynchronous work. A delayed first interaction after background inactivity locks before resetting the deadline. Backup verification is invalidated when inputs change, close, or unmount; restore decrypts and validates the actual envelope again.
- PDF.js 6 runs inside a dedicated, cancellable worker, with its own network-blocking response CSP. Only core text extraction runs: no scripting manager, viewer, HTML, links, attachment execution, remote resources, or OCR. Embedded document/page scripting is rejected. Size/page/text/row limits and a hard 20-second termination protect the UI. Errors shown to users contain static messages, not financial text or parser stacks.
- PDF review requires posted-date/year confirmation, complete-page/section review, type confirmation, and matching totals for every section. Missing/uncertain fields are flagged and editable. August rows remain in statement reconciliation but are excluded from tracking. Duplicate decisions occur in a second preview. Each bank profile was checked locally against one real statement; a first page that does not match the selected bank is labeled unvalidated.
- Build/runtime public configuration rejects service-role/secret keys and URLs containing credentials. Original PDFs, private data directories, environment files, and key files are ignored by Git. No financial analytics, AI calls, or payload logging are present. React renders imported descriptions as text; production uses a nonce CSP, frame denial, no-referrer, nosniff, no-store, and HTTPS HSTS.

## Test scope

The shipped migrations run in local PostgreSQL (PGlite) using compatible JWT helpers. Tests exercise anonymous/other-owner access, owner without MFA, loss of MFA after saving, strict payload validation, direct-write denial, accidental write grants, and competing versions. These helpers do not establish that actual Supabase tokens/MFA are configured properly.

Web Crypto tests cover encrypted records/settings, fresh nonces, wrong secrets, wrong recovery keys, modified ciphertext/nonces/wrappers, non-extractable keys, and complete encrypted backup restoration. A changed login password cannot decrypt the vault. Storage mocks verify authorization before each read/write. Production browser tests use synthetic PDFs with the actual maintained parser, including all three banks, malformed/scripted/blank/too-many-page inputs, mismatch blocking, no upload during parsing, and markup remaining text. Worker deadline/abort tests check termination.

## Limitations

- A malicious browser extension, compromised device, or malicious deployed application code can read data while unlocked. CSP, encryption, and MFA do not prevent an authorized bad deployment from stealing secrets. JavaScript garbage collection prevents guaranteed forensic memory erasure.
- Resource limits bound typical parser workloads but cannot promise zero temporary allocation spikes or eliminate every parser vulnerability. PDF extraction uses best-effort text profiles rather than bank-provided structured records. Reconciliation and owner review are essential; matching sums alone cannot prove each date/type is correct. Do not alter a statement total merely to pass reconciliation. Real Capital One/BofA layouts still need validation.
- Whole-vault encryption exposes identity, encryption parameters, ciphertext size, save timestamps, and version counts to Supabase. Supabase administrators can change policies/data, delete records, or replay an older valid ciphertext. GCM detects modification; it does not independently detect rollback of a previously valid vault. Keep offline encrypted backups.
- PBKDF2 protects a strong unique unlock secret; it does not make a weak secret safe from offline guessing. Use a password manager-generated secret or a long random passphrase. Keep the random recovery key separately. Losing both makes data unrecoverable. Authentication recovery restores login only; encryption recovery still requires the secret/key. Key rotation and automated recovery emails are not implemented.
- Saves reject stale versions instead of automatically merging devices. An unsaved conflict requires lock/unlock and reapplying the change. Restoring a backup replaces current state and adopts that backup's unlock and recovery credentials.
- No scanned/password-protected PDF support, OCR, bank linking, automatic background imports, or notifications. September requires adjacent statements when a cycle ends before September 30. Excel exports and offline recovery-key downloads are readable local files; protect them yourself.
